# Підказка «аудитор систем управління знаннями», версія v1

Та сама підказка подається двом моделям незалежно: Claude Opus 5 (роль A) і Claude Haiku 4.5
(роль B). Відповідь моделі B не показується моделі A і навпаки — це умова рівня верифікації V3.

```PROMPT
## 1. РОЛЬ
Ти — аудитор систем управління знаннями з досвідом впровадження KMS у державних і культурних
установах. Ти оцінюєш архітектуру критично: шукаєш не переваги, а місця, де система зламається.

## 2. КОНТЕКСТ
Організація: обласний художній музей, який веде облік музейних предметів і нерухомих пам'яток.
Проєкт: Domain Knowledge Hub — мінімальний KMS із шести шарів:
1) джерела: державний реєстр пам'яток, інвентарні книги, акти огляду стану, датчики мікроклімату,
   скани архівних документів, фото і 3D-копії, інтерв'ю з експертами, зовнішні тезауруси;
2) захоплення: імпорт CSV/SQL, збирання показів датчиків, OCR сканів, форми інтерв'ю, Git для
   markdown-документів знань;
3) опрацювання: нормалізація термінів за тезаурусом, дедуплікація, валідація схем, витягання
   тверджень за допомогою LLM, верифікація V1–V4, побудова ембедингів;
4) сховища: реляційна база обліку, файлове сховище медіа, граф знань (SKOS/OWL), векторний
   індекс, Git-репозиторій документів знань;
5) сервіси: повнотекстовий і векторний пошук, API запитів, рушій правил для тривог, RAG-асистент;
6) інтерфейси: робоче місце хранителя, дашборд мікроклімату, Git/CLI для інженера знань,
   публічний портал відкритих даних.
Наскрізні функції: права доступу, походження даних, якість, версіонування, метрики.
Обмеження: мала команда (2–3 особи), бюджет обмежений, частина даних має обмежений доступ,
установа працює в умовах воєнних ризиків.

## 3. ЗАВДАННЯ
Виконай три частини:
A. Запропонуй щонайменше 8 критеріїв порівняння платформ для сховища знань цієї установи.
   Для кожного критерію вкажи вагу у відсотках (сума всіх ваг = 100) і одним реченням поясни,
   чому саме така вага доречна для цього контексту. Обов'язково охопи готовність до роботи з
   LLM та керування правами доступу.
B. Назви рівно 5 ризиків цієї архітектури — конкретних, із механізмом реалізації, а не загальних
   формулювань на кшталт «низька якість даних».
C. Назви рівно 5 покращень, кожне з яких усуває щонайменше один із названих ризиків.

## 4. ФОРМАТ ВИХОДУ
Поверни ТІЛЬКИ валідний JSON без тексту до або після нього:

{
  "criteria": [
    {"id": "cr1", "name": "назва критерію", "weight": 0, "rationale": "чому така вага"}
  ],
  "risks": [
    {"id": "r1", "statement": "ризик із механізмом реалізації", "layer": "шар архітектури",
     "severity": "low|medium|high", "sources": []}
  ],
  "improvements": [
    {"id": "i1", "statement": "покращення", "addresses": ["r1"], "effort": "low|medium|high",
     "sources": []}
  ]
}

## 5. ПРАВИЛА
1. Сума ваг критеріїв має дорівнювати рівно 100.
2. НЕ вигадуй джерела, назви стандартів і цифри з документації платформ. Якщо потрібне
   посилання — залиш "sources": [], перевірку виконає людина.
3. Не називай конкретні продукти в критеріях: критерій має бути придатним для порівняння будь-якої
   платформи.
4. Ризики мають стосуватися саме описаної архітектури, а не управління знаннями взагалі.
5. Кожне покращення має посилатися щонайменше на один ризик у полі addresses.
6. Відповідай українською; JSON має бути синтаксично валідним.
```
